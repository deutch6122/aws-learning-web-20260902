CHAPTER 01

全体アーキテクチャと責任分担

最初に「1回のHTTPリクエスト」と「1回のデプロイ」が通る経路を別々に整理します。

ユーザー通信

  1. Route 53が名前をALBへ解決
  2. ALBが正常なEC2を選択
  3. ApacheがTomcatへreverse proxy
  4. JavaがSecretを取得してRDSへ接続

デプロイ通信

  1. CodeConnectionsがGitHub変更を取得
  2. CodeBuildがTerraformとWARをbuild
  3. S3 artifactをCodeDeployが取得
  4. hookで配置・DB確認・service検証
実務の視点

構成図には通信方向、protocol/port、認証方式、障害時の影響範囲を併記します。「サービスがある」だけでは運用設計になりません。

Q1ブラウザはRoute 53を経由してHTTPリクエスト本文をALBへ送る。

Route 53の役割はDNS名前解決です。HTTPリクエスト自体は、名前解決で得たALBの宛先へ送られます。

Q2ユーザー通信とデプロイ通信は経路も権限も異なるため、分けて設計・調査する。

ALB経由のWeb通信と、CodePipeline/CodeBuild/CodeDeployの管理操作では、利用主体・IAM権限・ログが異なります。

CHAPTER 02

VPC・Subnet・Route Table

public/privateは名前ではなく、routeとpublic IP、到達経路の組み合わせで決まります。

Public subnet
Internet Gatewayへのdefault routeを持ち、ALBとNAT Gatewayを配置。
Private app subnet
EC2を配置。外向き通信はNAT Gateway、またはVPC endpointを利用。
Private DB subnet
RDSを配置。Internet向けdefault routeを持たず、VPC内通信だけを利用。
Internet → IGW → public ALB
private EC2 → NAT Gateway → AWS public API / package repository
private EC2 → VPC local route → private RDS endpoint
コストと可用性

NAT Gatewayは時間・通信量課金があります。学習環境の1台構成と、本番のAZごとの冗長構成は目的が違います。S3 gateway endpointやSecrets Manager interface endpointとの費用・可用性も比較します。

Q3Subnet名に「private」と付ければ、Internetから自動的に隔離される。

名前は制御になりません。route table、public IP、IGW、Security Group、NACLなどの実設定で到達性が決まります。

Q4EC2から同一VPC内のRDSへは、通常NAT Gatewayを経由しない。

RDS endpointはprivate IPへ名前解決され、VPCのlocal routeで接続します。NATは主にprivate subnetから外部へ出る通信で使います。

CHAPTER 03

IAM・Security Group・Secrets Manager

IAMは「AWS APIを誰が操作できるか」、Security Groupは「network上でどこへ接続できるか」を制御します。

制御守る対象今回の例
IAM RoleAWS APIEC2から対象Secretだけを取得
Security Groupnetwork flowApp SGからDB SGの3306だけ許可
DB authenticationMySQLSecret内のusername/passwordで接続

Credentialを置かない

Access KeyはrepositoryやEC2の設定ファイルへ保存しません。EC2 Instance Profileから短期credentialを取得し、Secretの値ではなくARNだけを環境設定として渡します。

最小権限

secretsmanager:GetSecretValue のResourceを対象Secret ARNへ限定します。Terraform stateにもpasswordが保存され得るため、state bucketも機密情報として保護します。

Q5RDSの3306番portをSecurity Groupで許可すれば、IAM権限なしでもSecrets Managerからpasswordを取得できる。

network到達性とAWS APIの認可は別です。Secret取得にはIAM、RDS接続にはSGとDB認証の両方が必要です。

Q6Security Group参照を使うと、IP範囲ではなく「App SGを持つresource」からの通信に限定できる。

App SGをDB SG ingressのsourceにすることで、instanceのprivate IPが変わっても役割単位で制御できます。

CHAPTER 04

ALB・EC2・Auto Scaling

ALBは入口、Launch Templateはinstanceの設計図、Auto Scaling Groupは望ましい台数を維持するcontrollerです。

ALB

振り分け

listenerで受信し、target groupのhealthyなinstanceへ転送します。

Launch Template

再現可能な起動

AMI、instance type、IAM profile、user data、SGを定義します。

ASG

台数維持

desired/min/maxとhealth checkに基づきinstanceを補充します。

なぜ /health はDBを見ないのか

静的なApache health checkにより、一時的なDB障害だけで全EC2がunhealthyとなる連鎖を避けます。一方、深い正常性は別の監視やデプロイ検証で確認します。

実務の注意

health checkを軽くしすぎると業務障害を検知できず、重くしすぎると依存先障害で全targetを外します。livenessとreadiness、依存先監視を分けて設計します。

Q7ALBはtarget groupでhealthyと判定されたEC2へrequestを転送する。

listener ruleがtarget groupへforwardし、health checkに合格したtargetが転送対象になります。

Q8Auto Scaling Groupを使えば、アプリを保存したEC2を手動修正してもその変更は永続的に保証される。

instanceは置換されます。必要な設定はLaunch Template/user data、AMI、CodeDeployなど再現可能な仕組みに入れます。

CHAPTER 05

Apache・Tomcat・Java WAR

1台のEC2内でも、Web serverとapplication serverの責務を分離しています。

Apache :80

/health を静的応答し、その他をlocalhostへproxy。

Tomcat :8080

ROOT.war をcontext root / として展開。

Static + Servlet

index.html は教材、/api/status はJavaの動的API。

src/main/webapp/index.html  ┐
src/main/webapp/styles.css │  mvn package → ROOT.war
src/main/webapp/app.js     │
HomeServlet.java           ┘
今回の改善点

画面全体をServletで文字列生成せず、静的資材とJSON APIを分離しました。CSSがHTMLとして返るmapping事故を避け、教材だけの差し替えも容易になります。

Q9ROOT.war はTomcatで通常context root / として公開される。

Tomcatの命名規則によりROOT.warはroot contextになります。別名のWARなら通常その名前がcontext pathになります。

Q10CSSへアクセスしてContent-Typeがtext/htmlでも、HTTP 200なら配信は正常である。

200だけでは不十分です。CSS URLがfallback HTMLを返すと見た目が崩れます。Content-Typeとresponse bodyも確認します。

CHAPTER 06

RDS MySQLとAP–DB接続

JavaアプリがSecretを取得してからSQL結果を画面へ出すまでを追います。

  1. 1

    設定を読む

    systemd経由の DB_SECRET_ARN を参照。Secret値は設定ファイルへ書かない。

  2. 2

    Secretを取得

    EC2 Roleの一時credentialでSecrets Manager GetSecretValue を実行。

  3. 3

    JDBC接続

    host・port・dbname・username・passwordからJDBC connectionを確立。

  4. 4

    Queryと返却

    messages をSELECTし、JSON APIからbrowserへ返却。DOM挿入時はtextとして扱う。

デプロイ時

check_db.py が接続確認、seed_db.py がtableと初期データを冪等に作成します。

画面表示時

Java APIがRDSを参照します。失敗時はSecretやhostを返さず、例外classだけをstatusに表示します。

本番化の論点

connection pool、query timeout、RDS Proxy、TLS証明書検証、Secret rotation、migration tool、transaction境界を追加検討します。

Q11seed_db.py を複数回実行しても同じ初期データが無制限に重複しない設計が望ましい。

再実行可能な冪等性は、自動デプロイや障害復旧で重要です。CREATE IF NOT EXISTSや一意キーを利用します。

Q12Secrets Managerを使えば、Terraform stateにSecret値が入る可能性はなくなる。

TerraformがSecret valueを作成・設定するとstateへ保持され得ます。remote stateの暗号化、versioning、access制御が必要です。

CHAPTER 07

Route 53・ACM・HTTPS

domain名、証明書、listenerをつなぎ、利用者が検証できるHTTPS経路を作ります。

Route 53

Alias record

app.example.com をALBへ向けます。ALBのIPを固定値として登録しません。

ACM

Certificate

ALBと同じregionの証明書を用意し、domain validationを完了します。

Listener

TLS termination

443で証明書を提示し、80は443へredirectします。

Browser -- HTTPS --> ALB -- HTTP --> Apache
          TLS検証       TLS終端       private network
確認観点

DNS recordだけでなく、証明書のSAN、有効期限、region、443 listener、SG ingress、HTTP redirectを1本の経路として確認します。

Q13ALB用ACM証明書は、どのregionで発行しても同じように設定できる。

ALBへ設定するACM証明書はALBと同じregionに必要です。CloudFront用証明書のregion要件とは分けて覚えます。

Q14Route 53 AliasはALBの変動する宛先を名前で参照するために使える。

ALBの個別IPを固定せず、AWS resourceへのAliasとしてrecordを作成します。

CHAPTER 08

Terraformとremote state

構築手順ではなく、望ましい構成を宣言し、planで差分を確認してapplyします。

fmt表記を統一
→
validate構文・schema確認
→
plan変更差分を審査
→
apply実環境へ反映

S3 backend

stateをlocal端末から分離し、暗号化・versioning・access制御を適用します。

Lock

同時applyによるstate競合を防ぎます。利用するTerraform versionに合うlocking方式を選びます。

planの読み方

-/+ は置換です。RDS、ALB、Launch Templateなどの置換がdata消失や停止につながらないか、件数だけでなくresource単位で確認します。

Q15terraform plan が成功すれば、apply後のapplication疎通も保証される。

planは構成差分を予測しますが、起動script、networkの実疎通、アプリ動作までは保証しません。後段の検証が必要です。

Q16remote stateには機密値が含まれる前提でaccessを制限する。

sensitive = true はCLI表示を抑えますが、stateから値を消す機能ではありません。state自体を保護します。

サービス責務主な確認先
CodePipelinestage間の順序とartifact受け渡しaction execution

CodeDeployEC2へ配置しlifecycle hookを実行instance event diagnostics
調査の原則

Pipelineの赤いstage名だけで原因を決めず、execution ID → external build/deployment ID → 詳細logの順に辿ります。異なるexecutionのstage状態を混ぜないことも重要です。

Q17CodePipelineのIAM RoleにGitHub repositoryへのaccessがあれば、GitHub App側のrepository許可は不要である。

AWS側のUseConnection権限に加えて、GitHub App installation側でも対象repositoryへのaccessが必要です。

Q18CodeDeployのAfterInstallが失敗すると、ApplicationStartとValidateServiceがskipされる場合がある。

lifecycle hookは順序実行されます。AfterInstallでexit code 1なら後続hookへ進めずdeploymentが失敗します。

CHAPTER 10

Systems Manager・CloudWatch・SNS

運用経路を最初から設計し、SSH portや長期鍵に依存しない調査方法を用意します。

SSM

Session Manager

IAM認証とaudit可能な経路でprivate EC2へ接続。Mac側にはpluginが必要です。

CloudWatch

Logs / Metrics / Alarms

OS・Apache・Tomcat・app logとCPU等を集約し、しきい値を監視。

SNS

Notification

alarmの状態変化をemail endpointへ通知。subscription確認も運用手順に含めます。

Patch運用

Patch Baseline、Patch Group、Maintenance Windowで「何を」「どのinstanceへ」「いつ適用するか」を分離します。適用前後のbackup・再起動・health確認も計画します。

ログの安全性

Secret value、password、Access Key、connection stringを出力しません。障害調査に必要なerror class、request ID、件数などを残します。

Q19Session Managerを使えば、EC2へSSH ingressを開けずにshell操作できる構成を作れる。

SSM Agent、instance role、SSM endpointへの到達性、利用者IAM権限などを満たせば、TCP/22を公開せず接続できます。

Q20CloudWatch Alarmを作成すれば、SNS email subscriptionの承認前でも通知メールは届く。

Email endpointは確認メール内のlinkでsubscriptionを承認するまで通知を受け取れません。

TROUBLESHOOTING LAB

症状から次の一手を選ぶ

この構成で実際に遭遇しやすい事象をもとにした5問です。最初に確認すべき情報を選んでください。

CASE 01SOURCE_FAILED

Source stageが即時失敗。ConnectionはAVAILABLE、Pipeline RoleにもUseConnectionがある。

次に確認する項目は？

AWS側のConnectionがAVAILABLEでも、GitHub側のAWS Connector for GitHubが対象repositoryを許可していなければsourceを取得できません。

CASE 02HEALTH_CONSTRAINTS

CodeDeployが失敗し、AfterInstallのlogにMySQL接続timeoutがある。

最初の切り分けとして適切なのは？

socket.timeout はnetwork到達性を優先して調査します。warningは重要な保守課題ですが、今回の直接原因とは限りません。

CASE 03UNSTYLED_PAGE

HTMLは表示されるがデザインが崩れ、/styles.css はHTTP 200。

追加で確認すべき内容は？

Servlet mappingやfallbackによりCSS URLへHTMLが返ることがあります。status codeだけでなくheaderと本文を確認します。

CASE 04DB_API_FAILED

/health は200だが、画面のDB connectionだけ失敗している。

この状態から言えることは？

/health はDB非依存の静的応答です。Tomcat log、application log、IAM、Secrets Manager、DNS、SG、RDSを順に確認します。

CASE 05MIXED_EXECUTIONS

Pipeline stateでPlanはFailedだが、後段のDeployはSucceededと表示されている。

正しい調査方法は？

get-pipeline-state は各stageのlatest executionを示すため、異なるpipeline実行が混在することがあります。execution IDで揃えてaction履歴を確認します。
